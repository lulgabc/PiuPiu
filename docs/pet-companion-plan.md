# PiuPiu 宠物伙伴升级研究

> 研究时间：2026-11-19  
> 状态：v1 已在 2.20.0 实现（Canvas 2D 贴纸木偶 + 行为大脑），2.21.0 补充物种体色/花纹，2.22.0 落地 B 软糖豆身体 + F 随机配饰原型；2.24.0 起默认改为 12 只 Tiny Pets 逐帧精灵（2.25.0 起新增整屏消除玩法，宠物逻辑不变），旧木偶保留为回退与预览。本文保留为设计记录与后续 Rive 评估依据。
> 当前版本：2.25.2（每局随机 1 只 Tiny Pets 精灵；`?petbody=vector` / `?petbody=cut` 预览旧 Canvas 木偶）

## 1. 现状与真正瓶颈

当前宠物：

- 每局随机 1 只，12 种 emoji。
- DOM 节点：白色贴纸底 + emoji + 影子 + 拟声气泡。
- 每帧只写 `transform` 和少量 CSS 变量；没有独立渲染循环。
- 行为：随机选目标点 → 走/停 → 偶尔跳 → 偶尔叫；对落词、连击、暂停等只有少量反应。

性能不是主要问题。1 个 46–56px 的 DOM 宠物，每帧不到 1ms；真正的问题是：

1. **视觉载体是静态 emoji**，没有四肢、眨眼、耳朵/尾巴、重心变化，无法表现“活物”。
2. **行为是随机游走**，缺少目标、情绪、记忆、预期和反馈，因此看起来“死板”。
3. **动作没有动画原则**：没有预备、跟随、挤压拉伸、落地缓冲、转向倾斜，只有平移和整体缩放。

结论：优先升级“行为系统 + 角色表现层”，而不是先加一个更重的 3D/AI 方案。

## 2. “像一个伙伴”需要什么

建议把目标拆成 6 个可验证的能力：

1. **永远有微动作**：呼吸、眨眼、耳朵抖动、尾巴摆动、重心漂移；即使站着也不僵硬。
2. **会看**：眼睛/头会追随下落的词、手指、玩家点击位置；打对后会看向玩家。
3. **有预期和反馈**：跳之前下蹲，落地挤压，急停前倾，受惊后先缩再跑。
4. **有性格**：12 种宠物共享一套骨架，但速度、好奇心、谨慎度、话痨程度、跳跃习惯不同。
5. **有上下文**：词堆高低、危险线、连击、流星、暂停、结算、玩家 idle 时间都会改变行为。
6. **有声音和触感**：脚步、落地、哈欠、呼噜、不同情绪的叫声；点它会有回应。

## 3. 可选技术路线

### A. 继续用 emoji，只加程序化微动作

做法：保留 emoji 贴纸，增加呼吸、整体倾斜、挤压拉伸、跳跃弧线、影子缩放、表情 emoji 切换、粒子/尘土。

- 优点：1–2 天可做；零资源；零运行时；风险最低。
- 缺点：仍然是“会动的图标”，没有四肢和真正的视线，无法解决核心问题。
- 适合：作为第一阶段的过渡，不作为最终方案。

### B. Canvas 2D 贴纸木偶（推荐）

做法：保留 emoji 作为宠物的“脸/身份徽章”，在 Canvas 2D 里给它加一套轻量矢量木偶：

- 身体/肚子、耳朵、前爪、后脚、尾巴、腮红、阴影。
- 12 种宠物用 4 种体型原型 + 各自耳朵/尾巴/颜色/花纹配置。
- 用程序化动画驱动：步态、眨眼、瞳孔偏移、耳朵弹簧、尾巴弹簧、呼吸、跳跃预备/落地挤压。
- 表情通过眼睑、瞳孔、嘴形、耳朵角度组合，而不是换 emoji。

性能估算：

- 1 个 128×128 canvas，DPR 上限 2。
- 每帧约 15–25 个路径/图形，无滤镜、无实时阴影模糊。
- 单帧 CPU 预计 <0.5ms（桌面）/ <1.5ms（iPad）；远低于现有 Pixi 环境层。
- 无新增运行时依赖，离线友好。

优点：

- 完全可控的程序化动作，能混合、打断、叠加，不会像固定动画片段。
- 资源极小，12 种宠物可以共享骨架和部件库。
- 可继续沿用现有白边贴纸、主题色和 emoji 识别度。
- 不需要第二个 WebGL 上下文，对低端触屏更安全。

缺点/风险：

- 需要设计并实现一套矢量部件和 Canvas 绘制代码。
- 12 种宠物的“像不像”依赖部件配置；需要先做 2–3 只原型验证。
- Canvas 内没有 DOM 可访问性；宠物本来就是 `aria-hidden` 的装饰层，可接受。

**建议作为 v1 的正式方案。**

### C. Rive

做法：用 Rive 编辑器制作带骨骼、网格变形、状态机和事件的 `.riv` 角色；Web 端用 `@rive-app/canvas` 播放。

优点：

- 最适合“互动角色”：状态机、混合、骨骼、网格变形、事件、视线参数都很成熟。
- `.riv` 文件通常 10–50KB；状态机静止时会自动 settle，空闲 CPU 接近 0。
- 动作质量上限最高，适合真正的“伙伴”表现。

成本/限制：

- Web runtime（官方 2026-01 文档，brotli -9）：canvas-lite 约 **222KB**，canvas 约 **567KB**；不是零成本。
- 需要 Rive 编辑器和动画师；12 种宠物仍有大量绑定/美术工作。
- 引入 WASM、第三方格式和编辑器工作流；离线需要把 runtime 和 `.riv` 一起缓存。
- 如果以后要换渲染器，行为逻辑会被状态机绑定。

**适合：** 有专职动画师、追求最高动作质量、愿意接受 222KB+ runtime 与编辑器成本时。  
**不建议：** 作为第一版直接投入；先用小原型比较 Canvas 木偶和 Rive 的实际观感。

### D. 序列帧 / 精灵图

做法：每个动作导出 WebP/PNG 精灵图，Canvas `drawImage` 或 CSS steps 播放。

优点：

- 美术可控，动作可以非常细腻；运行时几乎零依赖。
- 对固定动作（跑、跳、欢呼）表现稳定。

成本/限制：

- 12 种宠物 × 6–8 个动作 × 8–12 帧，资源量很大；按每只 150–400KB 估算，全部约 2–5MB。
- 只能是固定片段，难以做实时视线、尾巴物理、平滑打断。
- 需要动画师逐帧制作；改动作成本高。

**适合：** 有 2D 动画师、只需要少量 Hero 宠物、能接受资源体积时。  
**不建议：** 12 只全量。

> 2.24.0 实作结果：选用 Tiny Pets 的 12 只同风格宠物，每只 4 个动作 × 8 帧、64px 单元，转成 512×256 无损 WebP 后单只 5–35KB，12 张合计约 148KB，远低于上面 2–5MB 的估算。代价是只有 Idle / Jump / Sleep / Happy 四段，走路用 Jump 代替，实时视线和尾巴物理交给移动/翻转与行为大脑补足。

### E. Lottie / Noto Animated Emoji

Google 的 Noto Animated Emoji 提供 CC BY 4.0 的 Lottie 动画，包含大量 emoji；`lottie-web` light 约 168KB（SVG only），完整版约 306KB；dotLottie 运行时约 100KB 级别。

优点：

- 可以低成本给 emoji 加“待机小动画”，不需要自己画。
- 文件小、矢量、离线可用。

限制：

- Noto 动画主要是“表情/手势”循环，不是走路、爬词堆、跳跃等运动动画。
- Noto 画风与 Apple/系统 emoji 不一致，会破坏现有贴纸风格。
- 不适合做实时状态混合；仍然需要 JS 控制移动。
- CC BY 4.0 需要合理署名。

**适合：** 临时验证“有动画的 emoji 是否更好”，或只做待机/庆祝 overlay。  
**不建议：** 作为完整宠物方案。

### F. 3D / 视频 / AI 行为

- three.js / 3D 模型：在 56px 的宠物上收益极低，下载、内存、电量成本高，不建议。
- 透明 WebM/视频：解码和电量成本高，iOS 兼容和首帧控制差，不建议。
- LLM/云端行为：延迟、隐私、离线不可用，不适合实时游戏；本地 utility AI 足够。

## 4. 方案对比

| 方案 | 活泼程度 | 新增运行时 | 资源体积 | 制作成本 | 实时互动 | 结论 |
|---|---|---|---|---|---|---|
| A emoji 微动作 | 低–中 | 0 | 0 | 低 | 中 | 过渡 |
| **B Canvas 2D 贴纸木偶** | **高** | **0** | **很小** | **中** | **高** | **推荐 v1** |
| C Rive | 最高 | 222KB+ | 很小（.riv） | 高 + 编辑器 | 最高 | 预算充足再上 |
| D 精灵图 | 高 | 0 | 2–5MB | 高（美术） | 低–中 | 有动画师再做 |
| E Lottie/Noto | 中 | 100–300KB | 约 1MB | 低 | 低 | 只做待机 |
| F 3D/视频/LLM | 高 | 很大 | 很大 | 很高 | 低 | 不推荐 |

## 5. 推荐方案

### v1：Canvas 2D 贴纸木偶 + 行为大脑

一句话：**保留 emoji 的身份和糖果贴纸风格，把它变成一个有四肢、会看、会 anticipation 的小木偶。**

组成：

1. **PetBrain（10–15Hz）**
   - 用 utility AI 给动作打分，而不是纯随机。
   - 驱动力：好奇心、精力、舒适、兴奋、困倦。
   - 动作：观察、散步、爬堆、跳卡、坐、梳毛、打盹、追流星、受惊、欢呼、蹭玩家、发呆。
   - 带 cooldown、最短持续时间、最近动作记忆，避免连续重复。

2. **PetMotion（60Hz）**
   - 弹簧/阻尼：尾巴、耳朵、身体重心。
   - 步态：脚步接触、身体上下起伏、左右倾斜。
   - 跳跃：下蹲预备 → 起跳拉伸 → 空中收腿 → 落地挤压。
   - 视线：瞳孔/头部朝向最近的词、手指、玩家。
   - 微动作：呼吸、眨眼、耳朵抖动、尾巴摆动、腮红/表情变化。

3. **PetRenderer（Canvas 2D）**
   - 一个 128×128 canvas，DPR 上限 2。
   - 共享骨架 + 12 套 species config。
   - 预渲染阴影/渐变，避免每帧 `shadowBlur`、`filter`。
   - 每个宠物只有 1 个 canvas；不新增 WebGL 上下文。

4. **PetSignals**
   - `word:spawn`：抬头/警觉/看向新词。
   - `word:settle`：受惊、缩身、往旁边跑。
   - `word:clear`：欢呼、跳一下、看向玩家。
   - `combo >= 5`：转圈/跳舞/叫一声。
   - `meteor`：先躲，再庆祝。
   - `danger`：紧张、贴地、减少大幅动作。
   - `pause`：坐下、打哈欠、趴下。
   - `over`：低头/难过；重新开始时恢复期待。
   - `pointermove/tap/hold`：视线跟随、蹭手、呼噜。

5. **PetAudio**
   - 复用现有 Web Audio bus，不新增音频文件。
   - 脚步、落地、哈欠、呼噜、情绪化叫声；按情绪改变音高/节奏。
   - 每秒最多 3 个宠物音效，语音朗读时自动压低。

### 为什么不是直接上 Rive

- Rive 的动作质量上限更高，但 222KB+ runtime、编辑器/动画师成本、12 只宠物的绑定工作量都不小。
- 现在只有 1 只宠物，Canvas 木偶已经足够把“活泼”拉满；先用小成本验证孩子是否真的更喜欢，再决定是否升级。
- 行为接口（PetBrain/PetMotion）可以和渲染器解耦；未来如果 Canvas 表现不够，可以只替换 PetRenderer 为 Rive。

## 6. 行为设计细节

### 动作表（示例）

| 动作 | 触发 | 表现 | 时长/权重 |
|---|---|---|---|
| 观察 | 新词出现/玩家移动 | 抬头、瞳孔跟随、耳朵前倾 | 短，频繁 |
| 散步 | 无聊 | 小步走、尾巴摆、偶尔停下 | 中 |
| 爬堆 | 词堆升高 | 找边缘、跳上词卡、探头 | 中 |
| 坐/梳毛 | 空闲 6s+ | 坐下、舔爪、看向玩家 | 长，低 |
| 打盹 | 空闲 15s+ / 暂停 | 趴下、闭眼、呼吸变慢 | 长，低 |
| 受惊 | 词卡落在附近 | 缩身、炸毛、跳开、回头看 | 短，强制 |
| 欢呼 | 打对词/连击 | 跳起、转圈、举手、叫 | 短，强制 |
| 追流星 | 流星出现 | 追着跑、抬头、最后躲开 | 中 |
| 蹭手 | 点击/长按 | 靠近手指、歪头、呼噜 | 短 |
| 紧张 | 词堆接近危险线 | 压低身体、耳朵后贴、少动 | 持续 |

### 随机性要“有记忆”

- 每个动作有 cooldown 和最近使用惩罚。
- 同样的受惊/欢呼可以有 2–3 个变体，随机选。
- 每只宠物有性格权重：兔子更好奇、乌龟更淡定、狗更话痨、猫更爱观察、青蛙更爱跳。
- 每局保留少量“临时记忆”：最近是否被吓到、是否刚欢呼过，避免机械重复。

### 微动作是“活”的关键

即使什么都不做，也必须有：

- 呼吸：身体 ±1.5–2.5% 缩放，2–4 秒周期。
- 眨眼：2–6 秒随机，快速闭合。
- 耳朵/尾巴：跟随身体延迟摆动。
- 重心：轻微左右漂移，不是完全静止。
- 视线：偶尔看向玩家/词/屏幕边缘。

## 7. 性能与体验护栏

### 预算

- 单帧宠物 CPU：桌面 <0.7ms，iPad <1.5ms，低端 Android <2.5ms。
- 1 个 canvas，最大 128×128 CSS，DPR 上限 2；不新增 WebGL 上下文。
- 每帧最多 25 个绘制路径；不实时使用 `shadowBlur`、`filter`、大渐变；阴影/底色预渲染。
- 不在帧循环里创建对象/数组/字符串；复用 path 和向量。
- 资源：v1 无新增下载；若未来 Rive，runtime + 12 个 `.riv` 需要计入 PWA 体积。

### 降级

- 触屏/低功耗：宠物渲染降到 30fps，减少粒子/次级抖动；主游戏仍 60fps。
- 暂停/菜单/结算/后台：停止或冻结宠物更新（现有循环已具备）。
- `prefers-reduced-motion`：保留呼吸/眨眼，关闭跳跃、抖动、转圈和粒子。
- 危险线附近：降低动作幅度，避免遮挡和分散注意力。
- 宠物只占场地底部约 20–25%，气泡不遮挡下落词；点击热区只覆盖宠物本体。

### 测试矩阵

- iPhone SE / iPhone 12 / iPad 9。
- 低端 Android（Chrome，CPU 4× throttle）。
- 320 / 390 / desktop。
- 三套皮肤、中文/法语/英语、减少动态效果、离线。
- 指标：FPS、单帧耗时、长任务、内存、首屏时间、PWA 体积、音频事件频率。

## 8. 分阶段落地

### Phase 0：行为原型（1–2 天，低风险）

- 用现有 emoji 加 utility AI、视线、呼吸、预备/落地、更多游戏事件反应。
- 用 `?petbehavior=2` 开关灰度；不改视觉资产。
- 目的：验证“行为”本身能带来多少提升，建立体验基线。

### Phase 1：Canvas 木偶原型（约 1 周）

- 只做 3 只：小老鼠、小青蛙、小猫。
- 验证贴纸 + 四肢/尾巴/眼睛的实际观感、主题适配、320px 可读性。
- 和 Phase 0 的 emoji 版做 A/B 截图/录屏对比。

### Phase 2：12 只全量（1–2 周）

- 抽象 4 种体型原型 + 部件库。
- 逐只配置耳朵、尾巴、花纹、颜色、性格权重、叫声。
- 完成脚步/落地/哈欠/呼噜等音效和减少动态效果。
- 性能回归测试后上线。

### Phase 3：可选升级 Rive

- 只有在 Phase 2 的观感仍不够、且有动画师/预算时再做。
- 保持 PetBrain/PetSignals 不变，只替换 PetRenderer。
- 先做 1 只 Rive 与 Canvas 版对比，再决定是否全量。

## 9. 主要风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 动画过度，分散读词注意力 | 体验下降 | 底部活动区、危险时降频、气泡避让、可关闭/减少动态 |
| 12 只宠物风格不统一 | 像拼凑 | 4 种原型 + 统一贴纸描边/阴影/色板 |
| Canvas 绘制代码难维护 | 迭代慢 | 部件化、配置驱动、行为与渲染解耦 |
| Rive 运行时/编辑器成本 | 体积/预算 | 先 Canvas；Rive 只做可选替换 |
| 音频事件过多 | 烦躁/性能 | 每秒上限、冷却、语音时 ducking |
| 随机宠物缺乏连续性 | 不够“伙伴” | 局内记忆、开局自我介绍、对玩家名字/操作的即时反应 |

## 10. 建议的验收标准

- 任意 10 秒观察窗口内，宠物至少出现 5 种不同微动作/行为，不出现超过 0.8 秒的完全静止（睡眠除外）。
- 对落词、打对、连击、流星、暂停、结算都有可辨认的反应。
- 点击/长按有反馈；视线能跟随手指/词。
- 320px 宽度不遮挡关键 UI，不抢输入焦点。
- 60fps 主循环下，宠物单帧成本低于预算；低功耗模式 30fps 稳定。
- 首屏和 PWA 体积增加可控：v1 目标 <100KB 代码/资源；Rive 方案另行评估 222KB+。
- 减少动态效果下仍保留呼吸/眨眼，不出现跳跃/抖动。
